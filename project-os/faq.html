ProjectOS 新手 FAQ（2026-09-25 初版）

> 本檔是**常設文件**（跟著 repo 迭代），不是一次性產物——所以它落戶在

> app/ 並經 .project-os/config.toml 的 primary_whitelist 申報合法。

> 這本身就是「如何為常設文件落戶」的示範：不申報的陌生檔案會被

> reconcile 搬走或隔離，申報了就是基礎設施。

> 答案體例：**一句話答案** → 解釋 → 命令。

---

從哪開始

先說想解決的問題；沒有具體問題可說「用 project-os-guide 介紹全貌」。

導覽不操作專案。要實際檢查時，給出專案路徑並說「檢查這個專案有沒有亂放」。

前提：Host 可使用 Plugin；專案操作另需已部署的本機 project-os，引擎版本用 project-os --version 核對。

ChatGPT 雲端不能啟本機 stdio，僅有 Skill 不代表可操作本機專案。

預期看到本輪範圍、觀察、證據及未驗；成功是取得實際檢查結果，不代表已搬移或已驗收。

安裝更新前讀同版 PLUGIN-RELEASE.md，先核分發來源及 Host 正常安裝通道；有包不等於已載入。

需要留報告再明說「把本輪已做檢查留報告」；未授權時不因教學自動建立檔案。

H. 故障與誤操作（救命區，先看這裡）

H1 跑指令出現「不是受管專案：找不到 .project-os/config.toml」？

**該目錄還沒啟用治理**（或 --project 路徑打錯）。

.project-os/config.toml 存在即受管，這是唯一的判定。

```bash

project-os init --project /正確/路徑 # 啟用；或檢查路徑有沒有打錯

```

H2 我的檔案被搬走了！去了哪？

**被「整理」了，沒丟**。Primary 開發區之外的產物檔（md/pdf/xlsx…）

會被搬到 outputs/review/_YYYYMMDD_標題/（日期取檔案 mtime）。

```bash

project-os reconcile --project . # 看報告最後印的路徑；報告檔在 .project-os/reports/

```

不想要某區被動 → 把它申報為 dev_zones（見 C5）。

H3 檔案進了「隔離區」是什麼？怎麼取回？

**inbox 是待處理佇列，不是垃圾桶**——規則認不得的東西放這裡保命，

永不刪除，且每次 reconcile 按當前政策重新評估（有第二次機會）。

```bash

project-os inbox list --project . # 看 pending

原路徑已變合法 → 重跑 reconcile 自動還原

要搬去新位置 → 人工授權（必填理由，引擎不猜）：

project-os inbox enroll <inbox 路徑> --to <新位置> --by <你> --reason <理由> --project .

project-os reconcile --project . # 執行搬移

```

**enroll 只對「classifier 已知去處」的物品有效**（立案，

2026-10-15 裁）：授權是為 classifier 的歸位意見蓋章，不是指定新去處。

原路徑 classifier 認不得（unknown-collection）時，promote 決定**不可

執行**——報告會標 inbox.decision-inert（決定留痕但不驅動搬移）。

此類物品的合法出路只有兩條：① 申報集合／dev_zone 使原路徑變合法

→ 自動還原；② 人手工搬（決定照寫 enroll 留痕）。

H4 撞名或重複檔案會被覆蓋嗎？

**永不覆寫、永不刪檔**。同名異內容 → 後到者加穩定後綴 _1，兩份都留。

這是寫進產品靈魂的承諾（但注意：這不等於備份）。

H5 我誤刪了 `.project-os/` 會怎樣？

**重新 init 即可復管**（config 會重建、骨架檔「已有不覆寫」不會傷及你的內容）。

損失的是 reports／quarantine.log 歷史（觀測紀錄，非產品本體）。

產物歸位規則全在 core 裡，專案內沒有第二套邏輯會消失。

H6 上傳 401／403？

**401＝帳密錯（身分驗證）；403＝授權不足（過了驗證但沒權限）**——

兩層分開查，這個判讀法對任何 registry 通用：

- 401：帳密／token 錯，或該用身分拿錯憑證（password 要用該 service

**自己的** API key／htpasswd 密碼）。

- 403：過了驗證但沒權限——帳號沒被掛上該 repo 的上傳角色。

〔退役備查〕0.13.3 前主通道為 Cloudsmith，其專屬排查（完整 slug、

Access control 掛角色）隨通道退役；現行 pypiserver 的憑證管理見

D3（以各倉 release.yml 註釋為準）。

H7 照抄多行命令出現 `zsh: command not found: #` 或 `refspec does not match any`？

**行尾的 # 註解 不會被 zsh 剝掉**（zsh 互動模式預設不吃行尾註釋），

# 會變成真的參數傳給程式。食譜裡的註解行是給人看的，貼上時刪掉，

或先執行 setopt interactivecomments。0.2.1 實戰貨真價實踩過：

git push origin v0.2.1 # 註解 變成三個 refspec 報錯——好在 tag 已被

前一條 push 順帶推上（見 H8），虛驚一場。

H8 Actions 頁一堆紅 ×，是不是發佈失敗了？

**紅 × 是「調試軌跡」，不是「發佈失敗」——兩個頁面講兩個故事**。

Releases 頁＝產品史（每個版本最終都出貨了，失敗的 run 後來靠修復重跑

或手動補建收場）；Actions 頁＝工程史（每個紅 × 是一個被修掉的真 bug）。

讀法：發佈成功率看 Releases（應 100%）；流水線成熟度看綠剔——綠剔

出現在**最後一次** run 才正常（代表調試收斂，而非運氣）。

本倉實錄：6 次 run、5 紅 1 綠——前 5 次各卡死一關（測試幾何、token

兩層權限、shell 語法、GITHUB_TOKEN 寫權限），全修復後 v0.2.1 首次

零人工端到端。紅 × 是化石層，留著當教材，別刪。

H9 專案改名（目錄更名）怎麼做才不斷資料？（過渡橋＝symlink／符號連結）

**改名要由綁定該專案的 agent 從「上層目錄」執行（mv 與建橋同一口氣、

零空窗）；用戶只負責之後用新路徑開新 session——接線全是 agent 的事。**

**關鍵字互通**：本條的「建橋」＝ symlink＝符號連結＝ln -s 舊名指向新名，

搜尋時任一套詞都應命中本條。（2026-10-23 事故：搜尋只用 "symlink" 而

文件寫「建橋」，加上外層 .gitignore 遮蔽 app/，SOP 在場卻沒被找到，

遷移漏建橋——兩個檢索陷阱都已在此標記。）

改名斷的全是「記住舊路徑的外部綁定」（Host session 的 workDir、

其他工具的專案參照），引擎本身無感：config.toml 不存專案名，

reconcile --project 只吃路徑。

**常見事故**：用戶在 Finder 手動改資料夾名 → 正在工作的 session 立刻

Workspace path not found。原則：**改名永遠由 agent 執行**——agent 改完

立刻建橋；用戶手改沒有這一步，正是斷裂成因（2026-10-20 實戰：Zeabur2

Railway_Dev → Hosting Infrastructure_Dev）。

```bash

0. 在專案的「上層目錄」操作（執行者自身 session 才不會失去路徑）

cd <專案上層目錄>

1. 確認專案內無自引用（有命中先改內容）

rg -l "OldName" OldName_Dev/

2. 改名＋建橋同一行（先建橋再改名不可行：橋要有新名字才指得過去）

mv OldName_Dev NewName_Dev && ln -s NewName_Dev OldName_Dev

3. 機械驗證（綠燈載體：命令自檢）

project-os reconcile --project NewName_Dev # 全綠 = 引擎面完成

4. 逐 Host 遷移綁定（清單見下）；全部遷完才拆橋

rm OldName_Dev # 只刪連結不刪資料；刪前確認無活躍 session 仍綁舊路徑

```

**用戶面指引**：改名期間舊 session 不會斷（橋接住了），之後一律用

新路徑開新 session——舊路徑是臨時支架。看到 `Workspace path not

found` 時，用戶只需對任何 agent 說「專案改過名，幫我接回線」，agent

三步：看 <專案上層> 有無 OldName_Dev -> NewName_Dev 橋 → 無橋

建橋（先確認新目錄存在）→ 指引用戶新路徑。用戶不需、也不應手動搬

檔案或改設定。

逐 Host 檢查：Kimi Work（舊 session workDir 寫舊路徑，橋接住不斷，

側欄顯示名仍舊；徹底清理需退出 Host 改內部記錄）；Codex／Claude 等

各 Host 設定檔；dotfiles／密碼管理／其他專案文件（rg 新舊名都掃）。

警告：symlink 是**有期限的支架**——拖越久，透過舊路徑新產生的綁定

越多；有些工具會 canonicalize 路徑（真實新路徑寫入設定），無害，

但拆橋前的掃描要認得新舊兩個名字。

**與 Q5 的關係**（）：Q5 否決的是

「永久 symlink 路標」當常設機制（drift 源）；本橋是**過渡設施**——

遷完即拆，正是 Q5 認可的「登記後到期清理」變體，兩者不衝突。

忘記建橋的補救：舊路徑 ln -s 指回新位置即可續命（2026-10-25

ProjectOS_Dev 實戰驗證），仍須補跑本條第 3 步機械驗證。

H10 可以在專案內的內層 repo 再跑一次 `project-os init` 嗎？

**不可以——一專案一台引擎，治理不巢狀**（owner 2026-10-30 裁；

Q3）。內層 repo（primary 裡自帶

.git 的子目錄，如 workspace/Layouts_Norm/）是外層專案的工作

產物，不是獨立治理對象；在裡面 init 會造出巢狀

.project-os/config.toml，兩台引擎對同一棵樹各自分類搬移，

「唯一保證來自事後 reconcile」立即失效。

內層 repo 的保護方式＝在外層 .project-os/config.toml 申報

dev_zones（路徑段名稱比對，一 repo 一名；見 C4）。若內層

repo 長大要獨立受管，把它**搬出**專案 root、成為獨立專案再

init——巢狀永不合法，沒有豁免通道。

A. 身份與關係

A1 core 和我的 `.project-os/` 是什麼關係？

**規則住 core（一份，裝在你主機上）；記憶住專案（每個專案自己的 .project-os/）。**

core 是無狀態的批次工具，.project-os/ 裡只有 config＋歷史紀錄，沒有程式碼。

升級 core＝所有專案行為一起更新，不需要對各專案推送任何東西。

A2 把專案搬到別台主機／換電腦會怎樣？

.project-os/ 跟著專案資料夾走（記憶不丟）；新主機裝好 project-os

命令（見安裝章節）即可接手。新主機的 core 版本可以不同——報告會記

core_version，版本差異可診斷。

A3 「車與工廠」是什麼意思？

**車＝registry 裡裝好的成品（pipx 裝的那個）；工廠＝開發倉的源碼。**

日常使用（reconcile/audit）用車（穩定、與 fleet 同版）；開發改碼才進廠。

A4 reconcile 會動到我的原始檔案嗎？

**會「搬動位置、不會刪內容」**。開發區（dev_zones）內的一切原封不動；

區外的產物被歸位；規則認不得的進隔離（可救回）。拿不準就先

reconcile --plan（零寫入預覽）。

A5 ProjectOS 治理自己時有沒有「開外掛」的機制？

**沒有，也不允許有**（owner 2026-11-05 裁：機制均等原則）。

每個開發 repo 都是**自己產物的工廠**——產物按類型分發到各自的

管道（web → VPS／Supabase／Vercel；Python 包 → pypiserver；node

包 → registry；Norm 記錄 → install.sh 落地 ~/.local/share/standards…）。

ProjectOS_Dev 只是「引擎」這個產物的工廠，是**第一個治理對象

（dogfooding）**，不是特權物件。

層次切分（owner 2026-11-05 再裁）：

- **規則層＝各專案自由**：每個專案有自己的開發物與特殊規則，

這當然合理——ProjectOS_Dev 的 AGENTS.md 比車載模板多出審計尺

五問、每切片收尾跑 audit 這類「專案特化規則」，屬此層，允許存在。

- **機制層＝三重靈魂通用**：「整理師」「防 Scope 爆炸」「防漂移」

的對帳機制（reconcile／audit／preflight／紅綠燈／教義鏈…）是

**所有受管專案通用的基本標準**，是 ProjectOS 對受管專案的服務

承諾——不許結構性差異。任何機制若在 ProjectOS_Dev 有效、在其

他專案結構性失效（如教義鏈曾硬編碼它的檔案路徑），即為產品缺陷，

比照 drift 處理。

A7 每個專案都該有自己的教義嗎？怎麼建？（，2026-11-12 裁）

**開發型底座（app／workspace）的專案：是，且 init 已自動建好**——

教義＝專案自己的憲法（root 閉集、權威鏈等最高結構法則的正本），

config.toml 會有 doctrine_path 指向它。hub／norm 底座的 init

只提示不自動建：norm 專案的憲法即 Norm 正本家族（STD-POL0 體系

總則），自動建會雙頭馬車；確有需要再手動跑

project-os doctrine init。非開發型底座（sop／research／campaign／

course）不建。

**怎麼改**：正文（修正案索引段以下）不可就地編輯——任何變更走

修正案（實體包入 同版需求來源（內部定位已裁剪）＋索引登記

典範 sha256），audit 的 DOCTRINE_INTEGRITY 會對帳，就地偷改會被

finding 抓出。教義只管「永遠不能做的」；產品邊界（現階段做／不做

什麼）是 MVP 宣告，住 governance/，兩者不同層。

A6 `--by` 的 canonical 署名是什麼？（M-5，）

**每個 host 一個字串：<宿主產品名> / <模型>。** 同一 host 一字串，

actor.multiple finding 才保有真警訊力（實彈：同一台機器 30 天內

Claude 家族出現 5 種寫法，finding 從警訊退化成噪音）。

| host | canonical | 常見變體（歸一到左） |

|---|---|---|

| Claude Code | Claude Code / <模型> | Claude Code Desktop / …、Claude / …、Claude Cowork / …、斜槓前後無空格 |

| Kimi Work Desktop | Kimi Work Desktop / <模型> | Kimi Work / … |

| Codex | Codex / <模型> | |

| Cursor | Cursor / <模型> | |

| Gemini | Gemini / <模型> | |

| Trae | Trae / <模型> | |

| Antigravity | Antigravity / <模型> | |

reconcile 對已知變體會在 finding 裡附**歸一建議**（自報≠驗證：

只建議、不強改）。新 host 進表＝FAQ 改版（車載文件隨 wheel 發行）。

B. 安裝與環境

B1 pipx 是什麼？為什麼不用 pip？

**pipx＝每個 CLI 工具一間獨立隔離套房**（專用 venv），套件間不相汙染、

解除安裝乾淨。pip 裝進系統 Python 大家擠一間，容易撞依賴。

B2 Python 要哪個版本？

**3.11 或更高**（這是硬性要求，安裝腳本會先檢查）。macOS 用 Homebrew

或 python.org 裝新版即可。

B3 裝完打 `project-os` 說 command not found？

**PATH 還沒生效**。重開 terminal，或：

```bash

python3 -m pipx ensurepath && exec $SHELL -l

```

B4 `~/.local/bin/project-os` 就是全部程式嗎？

那是**發動機鑰匙孔**（symlink）；真正的程式在 pipx 的 venv 裡

（~/Library/Application Support/pipx/venvs/project-os/）。

C. 啟用與日常治理

C1 怎樣算「受管」？

**.project-os/config.toml 存在即受管。** 沒有它，project-os 對該目錄

一律不動（fail-fast 提醒，不會誤傷）。

C2 既有專案（已有一堆檔案）接上來會發生什麼？

**首跑先預覽，看清楚了再真跑**：

```bash

project-os init --project /path/to/既有專案

project-os reconcile --project /path/to/既有專案 --plan # 只看預計動作，零寫入

project-os reconcile --project /path/to/既有專案 # 確認無誤後真跑

```

外來倉首納管也可在 config.toml 設 first_intake = true（只報告不動手，

人審後改回 false）。**2026-10-15 Q1 補**：非空 root 的 init 會

**自動開** first_intake 並列出既有內容；人審通過後用

project-os intake done --by <你> 機制化關閉（不須手編 config）。

首次納管的完整標準作業見車載 **PLAYBOOK.md**（project-os docs 可讀）。

C3 檔案命名有什麼規矩？

產物要**日期包裹**：outputs/review/_20260925_標題/（底線開頭、8 位日期、

1–80 字標題）。散置的產物檔 reconcile 會自動包裹歸位，日期取 mtime。

C4 root 層能自己開新目錄嗎？

**預設不行——root 是閉集**（.project-os/、AGENTS.md、inputs/、outputs/、

.artifacts/、primary、governance/、handoff/ 八項）。要開工具目錄（如

bin/、.github/）先在 config.toml 申報：

```toml

dev_zones = ["bin", ".github"] # 聯集語義：在預設上追加，不影響其他鍵

```

dev_zones 是**路徑段比對**：裸名 research 同時保護 root 層與 Primary

內任何層的 research/；不支援含 / 的寫法（safe-segment 驗證拒絕）。

**root 單一「檔案」要申報**（2026-10-15 Q5 補）：

```toml

primary_whitelist = ["CLAUDE.md"] # root 層精確檔名豁免（root.whitelist LEAVE）

```

**Host 指示檔**（CLAUDE.md／GEMINI.md 等各 Host 的專案級指示檔）

的受認可申報方式就是 primary_whitelist——八項閉集外的單檔例外，走

白名單、**不走日期包裹**。不申報的指示檔會被當「區外產物」歸位

（內容不丟，但不再是指示檔該在的位置）。

**車載文件自動認定**（2026-10-16 起）：隨 wheel 發行的文件

（project-os docs 列出的檔名：FAQ／GLOSSARY／PLAYBOOK／AGENTS 模板）

在 Primary 根層視為**公認基礎設施**，不須申報——既有專案升級引擎後，

新出現的車載文件不會再被首輪 reconcile 歸位（0.8.0 PLAYBOOK.md

實彈修復）；primary_whitelist 申報降為額外豁免的補充手段

（Q1/Q2 已裁）。

C5 AGENTS.md 是什麼？我要寫什麼？

**給 AI 助手看的「家規」入口**（init 自動生成模板）。檢查你有沒有要補的：

開發區清單、inbox 紀律、skill 產物放 .artifacts/skills/ 等。已有不覆寫。

C6 一個專案可以有幾個 Primary？混合內容／多 app 怎麼放？

**恰好一個**。八型（app/sop/research/campaign/course/workspace/

hub/norm）是底座契約閉集（hub＝GitHub Hub Repo 家族

*_Hub：協議／規範正本集合，四區

catalog/vendor/_sandbox/_archive＋必要根層檔案；

norm＝規範正本家族 *_Norm：已定/草稿兩區＋判例表紀律；

立第七型、覆議 repohub→hub＋norm），

init 擇一（config primary = 單值，

load_policy 閉集驗證）；多 Primary 不立案。

**型名宣告的是「底座契約」——這個 Primary 用哪套骨架＋開發區規則——

不是內容普查**。像餐館執照登記「中餐館」：宣告的是適用哪套規範，

不承諾菜單上每一道都是中餐。所以 research/ 專案裡有個 app/

子目錄完全不矛盾。

- 混合內容 → Primary 內部自由擺（如 research/app/）；不同子樹要不同

規則就用巢狀 AGENTS.md（業界慣例；Primary 內部本來框架自治）。

- 多 app（monorepo）→ Primary 內部 apps/ + packages/；repo 根就是

Primary，turbo / nx / pnpm workspaces 對 repo 根的要求在這裡全部滿足。

- 一 Primary 可掛多 provider（providers = ["x", "y"]，Slice 7a 已定案）。

語義權威：同版需求來源（內部定位已裁剪）。

C7 root 的八項與收集器字典

**定義正本在此（各專案通用，不隨底座變）**——治理面收集器存在的

意義就是存放開發中的一切；**primary 只放成品本身**。

| 項 | 定義 | 誰寫入 |

|---|---|---|

| .project-os/ | 引擎控制面：config、findings、報告（只放宣告與觀測，不放部件本體） | 引擎自產 |

| AGENTS.md | 自覺層入口指令（本檔的血統來源） | init 生成；兩層 repo 皆可編輯 |

| inputs/ | **素材收集器**——開發過程中進來的東西（四集合見下） | 人與 agent |

| outputs/ | **產物收集器**——本專案產出的東西（日期包歸位） | agent 產物＋引擎包裹 |

| .artifacts/ | 運行區：skill 產物、inbox 隔離佇列 | 引擎與 skill |

| <primary>/ | **成品的家**——只放成品本身（含成品在各生命週期的態，如草稿） | 各底座契約定義其內部結構 |

| governance/ | 採納規則（schedules.toml／core.md） | 引擎骨架＋人 |

| handoff/ | 跨 session 接力狀態 | agent |

**inputs/ 四集合**（分工與實例）：

- requirements/＝本專案**自造規格與機制的立案稿**（變更前送裁）。

⚠️ 同名解歧：這是「本專案自己的立法處」，**不是**引擎的需求

文件——引擎需求文件住工廠，受管專案的 agent 不讀（rule 10）。

- sources/＝外部原始素材（設計總結、收到的規格書……）

- references/＝外部參照與討論紀錄（調研、比較、會議記要）

- feedback/＝回饋（試用回報、審查意見）

**outputs/ 階段**：review/＝AI 產物歸位（日期包、append-only，

日期取 mtime）；published/＝對外發佈的成品。

**邊界句**：開發過程中的**非成品文件**（判例表、討論稿、工作筆記、

驗收基材）一律進收集器（inputs/ 或 outputs/ 日期包）；primary

只放成品本身（含其組成部分，如 app 底座的測試、norm 底座記錄內的

示範檔）。區分口訣：「**這是不是成品本身？**」是→primary；否→收集器。

（已裁；實彈前科見

doctrine-cases.md 判例 1。）

C8 維護窗口（pause）是什麼？

**暫停 reconcile 的「執行面」**——期間 reconcile 照跑、照寫報告

（觀測不停），但只報告不搬移；給「一段時間內整棵樹重組」（如分拆

前整備）用。**暫停是手術，申報是常態**：長期結構走 dev_zone 申報，

別反覆暫停。

```bash

project-os pause --project <路徑> --hours 24 # 開窗口（1–168h，預設 24，到期自動恢復）

project-os resume --project <路徑> # 提前結束

```

**只能由使用者親手執行**——agent 只能建議你暫停，不得自翻

（已裁）。窗口結束後的第一輪 reconcile

會把這段時間累積的待整理項一次攤開——免費的整備前後對照。

C9 scope.absent 一直提醒——持續營運專案一定要建 scope.toml 嗎？（session級mvp 丙案，18:22 裁決）

不一定。scope.absent 是「缺產品 MVP 邊界宣告」的觀測提醒

（drift 類、report-only）；若本專案為**持續營運**（無單一產品

MVP，Session 級交代走 handoff 三件式），owner 可於

.project-os/config.toml 親手宣告：

```toml

scope_mode = "off"

```

- **人裁，引擎不代判**：引擎不偵測專案型態（無後綴／名稱匹配）——

finding 一律只附建議文案，判斷永遠在人；宣告進 git，可審、

可回滾（刪鍵即恢復提醒）。

- **只關 absent 的 scope 面**：教義面（doctrine.absent／

doctrine.coverage）不受影響；值域僅 "on"|"off"，未知值

fail-closed。

- **矛盾提醒**：宣告 off 但 governance/scope.toml 仍存在（如有限

專項 stage）→ scope.mode-conflict（report-only）請二選一人裁：

移除宣告，或維持 stage——stage 的 form／review-due／boundary

對帳不受宣告影響。停用期間 reconcile summary 記

"scope_absent": "disabled-by-declaration" 一筆（觀測不消音）。

D. 發佈與分發

D1 打 tag 就會自動發佈嗎？

D2 成品放哪裡給人領？

**兩個通道同時發**：自架 pypiserver 的 internal/ 組（主通道；CI 經

發佈入口 pypi-publish.hojackywork.com 寫入，DEV-PTC1@5.0.0 Q2 起

改發 internal/）＋ GitHub Releases（兜底，registry 出事時的備援）。

使用者從 pypi-internal.hojackywork.com 領，開發者從 pypi.

hojackywork.com 領（唯讀掛載 internal/）。0.17.1 前發在 dev/ 組。

裝車一律走 registry，指令形狀見 F1。

〔退役備查〕0.13.2 前主通道曾為 Cloudsmith，備份於 0.13.3 退役——

legacy 機制的發鑰／撤權條目（E1/E2）留墓碑，不再適用。

D3 `project-os release init` 裝配完就能發了嗎？

**workflow 檔好了，還差平台層兩件事**：該 repo 推上 GitHub，並貼上

發佈 secrets（現行上傳憑證＝PYPI_PUBLISH_PASSWORD，發佈入口

pypi-publish 寫入 internal/；舊 PYPISERVER_PASSWORD（dev/）已退役；**確切變數名以各倉 release.yml 的註釋為準**——文件

不追代碼細節，正本在 workflow 檔）。之後打 v* tag 即全自動。

〔退役備查〕0.13.3 前為 Cloudsmith 三件套（CLOUDSMITH_TOKEN

secret；CLOUDSMITH_REPO／CLOUDSMITH_USER variables），隨備份

D4 中央模板在哪？新 repo 會自動套用嗎？

模板住在 hojackywork/ProjectOS_Dev 倉的 .github/workflows/release.yml

（GitHub reusable workflow 機制，必須寄存在某 repo）。**不會全自動套用**——

各倉要有一個 8 行呼叫檔，三個入口：release init 命令／建倉模板／手動貼。

模板改進在中央，全倉自動生效（要同步的只有「存在」，不是「內容」）。

D5 `status --json` 是什麼？（）

project-os status --json 把部署狀態總覽變成**機器可讀 JSON**

（schema_version＋tool／deployment／hosts／findings 四組，

欄位比照 MacGov 的 status --json）。findings 是觀測訊號：

plugin.stale（Host plugin 版號落後引擎）／plugin.not_detected／

connector.duplicate（獨立 mcpServers 與 plugin 內建 connector

並存＝工具兩套）／version.query_failed——**只回報、不自動處置**

，每條自帶 fix_hint 處置提示；最新版查不到時 latest_version

是 null、其他欄位照常。給 Agent 與儀表消費用；人類讀者維持

project-os status 文字輸出。

F. 版本與升級

F1 官方發新版後，我的專案要改什麼？

**專案什麼都不改；要改的只有「車怎麼升」。** registry 模式裝的車

（自架 pypiserver；0.13.2 前為 Cloudsmith，見 D2 退役備查），升級

用**帶版本號**的安裝指令（install.sh 或等價 pipx 直令）：

```bash

PROJECT_OS_INDEX_URL='<token URL>' sh bin/install.sh 0.4.0

等價：pipx install --force --index-url '<token URL>' \

--pip-args "--extra-index-url https://pypi.org/simple" project-os==0.4.0

```

**勿裸跑 pipx upgrade project-os**——0.4.0 實彈：它只認私有倉為

索引、解析不到 PyPI 上的依賴（mcp），會回報「已是最新」並停在舊版

（silent no-op）。升級後對每個受管專案重跑一次 reconcile——

政策即時生效、隔離區按新政策重估；config.toml 聯集語義，永不過期。

F2 為什麼版本號要三處一致？

**tag ↔ pyproject ↔ registry 同號是機器強制的**（A2 測試鎖住）——漏一邊

測試即紅。這是 Logto「missed version bump」事故給全行業的教訓。

G. 多機多 Agent

G1 兩台 AI Desktop 同時開著會搶著搬檔案嗎？

**排程只綁一台**（S1 教義）：每個受管專案只由一台 Desktop 跑定時 reconcile，

其他機器一律手動跑。手動 reconcile 任何時刻跑都安全（冪等、永不刪檔），

只是不要各自建 cron。

G2 `watch` 常駐行程是必須的嗎？它是每 3 秒跑一次 reconcile 嗎？

**不是必須，也不是每 3 秒跑 reconcile**。watch 是「輪詢快照比對」的

獨立行程：每 --interval 秒（預設 3）把全樹拍成

{路徑: (mtime, size, 是否目錄)} 快照，兩張完全相同 → 什麼都不做

（乾淨的樹零成本，連報告都不產生）；**有差異才代跑一次 reconcile**。

用輪詢而不用作業系統事件通知（FSEvents），是「host 不可信」公理——

跨平台唯一保證的公共底層是檔案系統本身。它掛了、沒開都不影響承諾：

任何時刻手動跑一次 reconcile 即全部合規。

G3 「給專案排個 reconcile」是什麼意思？reconcile 本身就是排程嗎？

**不是。reconcile 是動作（歸位），排程是觸發器（鬧鐘），兩層分開**。

project-os 是無常駐 CLI，自己不設鬧鐘；「排程」＝某台 Desktop 的定時任務

到點**呼叫** project-os reconcile --project …。日常說「排個 reconcile」

是省略句，全句是「排一個會自動執行 reconcile 的定時任務」。S1 教義

「每專案只綁一台 Desktop」管的是觸發器歸屬（誰有權設鬧鐘），不是

reconcile 本身。觸發三層：watch（輪詢代跑）／host 定時任務（到點代跑）／

手動 reconcile（最終保證）。

G4 外部 AI agent 要讀 ProjectOS 的治理知識，該讀哪裡？

**正式介面＝MCP／車載文件；過橋才釘 release tag；永勿直讀 main。**

repo 的 main 是工廠開發中狀態（無版本釘子、隨時漂移），不是知識介面。

正式介面（2026-10-12 裁決落地）：project-os mcp（19 Read／8 Draft Write 工具閉集，

含 docs tool）與 project-os docs（FAQ／GLOSSARY／AGENTS 模板隨 wheel

發行，有版本釘子）——安裝版升級後即隨車可用。升級前的人為過橋：

釘 release tag 讀（如 …/v0.3.0/FAQ.md，版本號隨當前 release）。

人類讀者維持讀工廠／GitHub 頁不變。

G5 讓 AI Host（Kimi／Claude／Codex…）用上 project-os 的 MCP，怎麼接？

**兩層：裝車（全機一次）＋接 host（每台一行設定，或一句 mcp install）。**

裝車見 F1；之後 pipx upgrade 升級對**全部已接 host 自動生效**

（設定只存穩定路徑、工具每次動態發現——升級永遠不用重接；

升級前開著的長 session 重開即愈）。

接 host 正典五台（條目共通形狀：command＝車版路徑

**驗收**：GUI host 重開後在設定裡看得到（且四工具 status／

drift_findings／declarations／docs 可呼叫）；CLI host 用自帶命令

讀取（如 claude mcp list）。

**車載 Skill 與雙入口（2026-11-22 Q1–Q7 已採）**：

想理解產品、名詞與使用時機，使用 **project-os-guide**；先說想解決的

證據解讀，不檢查當前專案、不修改專案或啟動測試。

想查詢或修改指定專案，使用 **project-os**；仍是唯一專案執行路由，

按同版流程及既有批准／人獨有分工處理。原三專項 Skill 已退出發行。

說「查詢 Plugin 工具」「查詢 CLI 工具」「查詢 FAQ」仍直交說明頁連結。

引擎自帶 Skill 正本在產品源的 skills/，隨 wheel 發行（DEV-PTC1

6.1.0 §1.3）；不是 Skills_Hub 或 host 快取。兩個入口皆為 Plugin 型，

隨同版 Claude／Codex／Kimi 插件包送達，不另裝中央 Skill 副本。

project-os deploy 為統一部署入口；包產生到

~/.local/share/project-os/plugin/dist/，宿主接入及升級依同版

PLUGIN-RELEASE 指引。Claude 正規通道為「外掛程式 → 新增 → 上傳

外掛程式」，Plugin 內只帶一個 MCP 連接器，避免舊註冊並存。

獨立型 Skill 才部署至中央 ~/.agents/skills/ 並由 host 指針引用。

安裝／部署不進 MCP；MCP 僅提供 Read 與未生效草稿 Write，實際閉集

以同版操作目錄為準。是否安裝由使用者決定，宿主不可代做的帳號操作

仍交人完成。

**部署精靈的寫入閘門**（切片 1；

DEV-PTC1 3.0.0 §8）：project-os deploy／undeploy 寫入前會先印

將執行的清單——互動環境問 [y/N]；**非互動（腳本／Agent）必須加

--yes**（過渡版未給只警告照跑、次版將拒動）。預覽用 --plan

（只列不寫）；選裝用 --only <host id>（可重複，只認各通道閉集）。

G6 雙層 git：工作區根的 repo 跟 GitHub 是什麼關係？

**外層（工作區根的 .git）純本地、無 remote、永不進 GitHub；進 GitHub

的只有 Primary（app/）的內層 repo。** 兩層分工：外層＝治理面版本化

（教義／需求／governance／handoff／控制面的歷史）；內層＝產品本體

（發佈通道，tag 觸發 release）。

- **既有專案納管**：project-os git-doctor --plan 先預覽，fix 一次性

遷移——含 .git/ 移入 app/（remote 存 .git/config 跟著走、歷史

不斷、可回滾；教義 §7 唯一合法路徑）。

- **外層 .gitignore 排除 app/＋.artifacts/**——兩層互不追蹤，

外層結構上追不到內層。

外層無-remote repo——fail-closed（報錯，不會誤推），但惱人；

這是紀律點，不是缺陷。

- **外層檔案（AGENTS.md／governance／handoff）的內容 Agent 可直接

G7 跨 session 交接（handoff）的標準做法是什麼？（2026-11-16 標準化）

**三件式：文檔＋prompt＋ticket。**

- **文檔**：狀態與事實住 handoff/（current.md 等）；請求類必附 prompt

備份段（備份先寫、照備份逐字貼、貼後凍結，備份帶交付註記）。

- **prompt（路由信）**：需路由者（**請求類或跨專案通報**）必須在對話

交付給 owner，由 owner 親手轉貼——**agent 不自行發送**；同專案沉底

通報免 prompt。三要件：發起方自報身份／要求接手方自報 Host＋Model

（治理命令帶 --by）／引用文檔全給絕對路徑；標明歸屬（session 或

專案兩粒度）、逐項分開（同專案合併須先經 owner 確認並留痕）。

- **先分流（2026-11-17 裁）**：機械維護（finding 自帶處置路徑）不發

prompt、不開票——finding 自然發現即通知；裁決類請求才走全制；

批量機械通報走「人審代遞」（另案）。

- **對話形狀（禁兩極端）**：對話必須同時含重點正文＋絕對路徑可點

連結；只丟連結或只講話不留連結皆禁止。

- **ticket（接力票）**：**票＝編號**——裁決類事項在 handoff 段帶

HO-TKT-YYYYMMDD-HHMM 即可；handoff/tickets.jsonl（append-only、

五欄）是機器掛點，人不主動維護。**關照無儀式**：機器可驗事項

（finding 消失／commit 落地）對帳自查自關、零回執；機器不可驗者

一句話回執即可。機械維護與純通報不開票。

- 詞表見 GLOSSARY「Handoff 層」；立案與裁決紀錄：ProjectOS_Dev

同版需求來源（內部定位已裁剪）。

G8 發版後要通報嗎？（2026-11-16，0.17.4 斷記實彈）

**要。發版＝需路由事件**——其他專案的 session 靠車版內容決定行為，

版號不會自己長腳。

- **沉底通報 must**：發版完成後在 handoff/current.md 記一筆（版號＋

內容一句＋驗證證據）。實彈：0.17.4 發版未記 handoff，下一個 session

拿舊版號誤判現況。

- **有專案等此版落地 → 請求類**：對話交付 prompt＋開票（標準見 G7）。

- **版號權威＝機器可查處**（git tag／pyproject）；handoff 記錄是通報，

不是版號權威——陳述版號前必先查，不靠記憶（含 AI）。

G9 多引擎寄居與教義對帳怎麼落地？（2026-11-16）

- **引擎狀態目錄**：一律寄居 .project-os/engines/<engine-id>/

（root 閉集不加頂；登記制——ls 即登記現況，未登記 id 被

engines.unregistered finding 點名）。各引擎 findings／reports

寫自家 engines/<id>/reports/；房東引擎對 engines/* 一律

LEAVE（權責邊界＝路徑邊界）。

- **教義對帳覆蓋**：每條教義條文要有對帳登記。引擎層正本隨 wheel

（canon＋矩陣）；專案層自持 governance/doctrine-map.toml

（同一 schema）；盤點／審閱用 project-os doctrine map。

無登記＝缺口不是豁免；機器不可驗的條文標 `machine_checkable =

false`＋理由（豁免＝人審債，audit 尾段列豁免清冊）。
